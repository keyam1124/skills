# 日本語ドキュメントをブラッシュアップする

テキスト編集者として、資料の種類と推定読者を読み取り、意味と根拠を保ったまま、読み手に伝わる日本語へ整える。

AI文体の除去そのものを目的にしない。AIっぽい表現は、根拠のない主張、冗長な表現、読者に合わない文体を見つけるためのチェック観点として扱う。

## 最優先ルール

- 入力にない事実、数値、固有名詞、背景、因果、評価を追加しない。
- 根拠のない具体化をしない。抽象表現を具体化したい場合は、本文中の既存情報だけを使う。
- 書き換え前に、資料種別、推定読者、読者の目的、前提知識を置く。読者が知らない内部用語や背景を前提にしない。
- 著者サンプルがない限り、一人称、主観、感情、人格、ユーモアを追加しない。
- repoドキュメント、仕様書、設計メモ、README、運用文書では、自然さより正確さ・検証可能性・簡潔さを優先する。
- 断定を強める場合は、入力文の根拠から言い切れる範囲に限る。判断材料が足りない場合は弱めるか、未確定として残す。
- 原文の役割を変えない。説明文を意見文にしない。仕様を提案にしない。注意書きを感想にしない。
- バージョン差があり得る機能、仕様、API、権限、プラン、コマンドの話は、公式資料またはrepo内の確認済み情報で確認できた範囲だけ書く。
- 公式資料やrepo内で確認できていない内容は、本文に断定として混ぜず、必要なら `確認できていない事項` として分ける。
- 出力は軽くする。依頼が単純な校正なら、原則として修正版だけを返す。

## タスク

日本語ドキュメントをブラッシュアップするとき：

1. **資料と読者の推定** — 資料種別、推定読者、読者の目的、前提知識を本文とファイル位置から読む
2. **依頼種別の判定** — レビュー、リライト、校正、レビュー後の修正版作成のどれかを読む
3. **読者に合わない箇所の特定** — 内部事情の列挙、未説明の専門語、過剰な抽象化、説明不足を探す
4. **AIパターンの確認** — 通常は5つの確認観点だけを見る。該当箇所がある場合だけ `references/ai-writing-patterns.md` の14パターンを参照する
5. **問題箇所の書き直し** — 読者に必要な順序、説明粒度、語彙へ整える
6. **意味と根拠の保持** — 核となるメッセージを変えず、未根拠の事実・意見・人格を足していないか確認する
7. **最終チェック** — 読者に伝わるか、定型表現が残っていないか、逆に意味を増やしていないか確認する

## 読者推定

書き換え前に、次を短く見立てる。通常は出力に書かず、読者前提が重要または曖昧な場合だけ補足する。

- **資料種別**：README、Getting Started、Install Guide、仕様書、設計メモ、ADR、運用手順、SNS下書き、記事下書きなど。
- **推定読者**：初めて読む人、導入したい人、実装者、レビュアー、運用担当、一般読者など。
- **読者の目的**：概要を知る、試す、実装する、判断の背景を確認する、運用する、投稿として読むなど。
- **前提知識**：本文だけで理解できるか、repo内の文脈や内部モデル名を知っている前提になっていないか。

repoドキュメントでは、読者に応じて説明粒度を変える：

- README は初見の導入者が読む。内部型名や実装都合の列挙より、「何ができるか」「どう使い始めるか」を優先する。
- Getting Started / Install Guide は試す人が読む。手順、前提、確認方法を優先する。
- Architecture / Domain Model は実装者やレビュアーが読む。正確な用語を残してよいが、初出では役割がわかる説明を添える。
- ADR は意思決定を確認する人が読む。採用理由、却下した案、影響範囲を優先する。
- AGENTS.md / 運用手順は作業者やエージェントが読む。実行条件、禁止事項、判断が必要な場面を曖昧にしない。

## 声の調整（任意）

ユーザーが自分の文章サンプルを提供した場合、書き直す前にそれを分析する：

1. **先にサンプルを読む。** 文の長さ、言葉遣い、文体、段落の始め方、句読点の癖、繰り返す表現、接続の仕方を見る。
2. **書き直しでその声に合わせる。** AIパターンを除去するだけでなく、サンプルのパターンに置き換える。短い文が多ければ長い文を作らない。
3. **サンプルなしの場合**、中立で簡潔な文体に整える。書き手の人格、体験、感情、意見は追加しない。

## 文体の調整

文章を派手にしたり、書き手の人格を足したりする必要はない。自然さは、余計な前置き・膨張表現・機械的な構造を落とし、本文の根拠と読者の前提に合う言葉へ戻すことで作る。

- repoドキュメントや技術文書では、推定読者に必要な情報を短く、具体的で、検証可能な文章にする。
- SNSや記事下書きでも、著者サンプルやユーザー指示がない限り、主観や一人称を増やさない。
- 感情や意見が原文にある場合は消しすぎない。ただし、原文にない感情や意見は足さない。
- リズムは整えるが、意味を増やすための余談や挿話は入れない。
- 原文が抽象的すぎる場合は、無理に作り込まず「この箇所は根拠不足」と短く指摘する。

## ブラッシュアップ時のチェック観点

詳細な注意語句、判定基準、書き換え例は、必要な場合だけ `references/ai-writing-patterns.md` を読む。通常は以下の5分類だけを確認する。

### 1. 根拠

入力文または参照資料にない内容を足していないか確認する。

- 重要性、意義、宣伝表現、比喩を足していないか
- 出典のない一般化をしていないか
- 効果、因果、将来予測を補っていないか
- 対象範囲、条件、例外を広げていないか
- バージョン差があり得る仕様、API、機能、権限、プラン、コマンドを未確認のまま断定していないか

根拠がない場合は、具体化せずに削る。必要なら `確認できていない事項` として分ける。

### 2. 構成

本文の情報量を増やさない定型表現を削る。

- 定型の導入、締め、展望がないか
- 見出し直後に、見出しを言い換えただけの空文がないか
- `まず`、`次に`、`最後に` が、手順ではなく文章の型として使われていないか
- 前置きが長く、本文の要点に入るのが遅くなっていないか

説明の順序は、書き手の事情ではなく読者の目的に合わせる。

### 3. 文体

自然さよりも、意味の明確さと検証可能性を優先する。

- 抽象語、AIっぽいビジネス語、官僚的な言い換えが多くないか
- `〜という`、`〜において`、`〜することが可能`、`〜という形で`、`させていただく` などの回り道がないか
- 主語なし、受け身、断定回避が、責任主体や判断をぼかしていないか
- 両論並記だけで終わり、判断条件が残っていないか

根拠から言える範囲では短く言い切る。判断材料が足りない場合は、未確定として残す。

### 4. 表記

同じものを同じ名前で呼び、読者に自然な語に戻す。

- 同じ対象を、問題、課題、懸案、イシューなどで言い換え続けていないか
- カタカナ英語を、意味の通る日本語に戻せないか
- 英日混在や翻訳調で読みづらくなっていないか
- コード識別子、API名、型名、DB relation 名を、一般語のように混ぜていないか

正式名称や識別子として必要な英語は残す。必要なら、初出で日本語説明を添える。

### 5. 形式

見た目の整理で、意味を補っていないか確認する。

- 箇条書き、太字、区切り線を使いすぎていないか
- 手順、制約、チェックリストではない箇所を、無理に箇条書きにしていないか
- repo文書、仕様書、運用手順に絵文字や会話フレーズが残っていないか
- チャットボットの返答のような締めや免責が本文に混ざっていないか

箇条書きは、手順、条件、比較、チェックリストでは残してよい。流れのある説明なら文章に戻す。

## repoドキュメントを直す場合

repoドキュメントを直す場合は、以下も優先する。

- 誰が何のために読む資料かを先に決める。内部事情の説明ではなく、読者の目的に沿う説明へ並べ替える。
- 原文、repo内の確認済み情報、公式資料だけを根拠にする。
- 存在確認していないコマンド、ディレクトリ、設定ファイル、機能、運用ルールを書かない。
- バージョン差があり得る機能、API、CLIオプション、設定項目、権限、プランは、公式資料で確認できた範囲だけ書く。
- 公式資料で確認できていない場合は、本文に断定として入れず、`確認できていない事項` に分ける。
- 「一般的には」「ベストプラクティスとして」だけで仕様を足さない。
- 主語を補う場合は、repo内で明らかな主体に限る。曖昧なら主語なしのまま簡潔にするか、確認事項に分ける。
- 文体は中立・実務的にする。熱量、断定、著者の気持ちは足さない。
- 箇条書きを無理に文章化しない。手順、制約、チェックリストは箇条書きのままでよい。
- 変更理由の説明を求められていない場合、長い講評を付けない。
- 英語の技術用語を残す場合も、日本語の助詞や語順に無理なく接続する。読みやすさを落としていれば、正式名称だけをコード表記で残し、説明文は日本語に戻す。

## プロセス

1. 入力テキストを注意深く読む
2. 資料種別、推定読者、読者の目的、前提知識を見立てる
3. 依頼がレビューか、修正版作成か、両方かを判定する
4. 読者に伝わらない原因を特定する。内部事情の列挙、未説明の用語、説明順序、粒度、根拠不足、文体の不自然さを分けて見る
5. レビュー依頼なら、AI文体だけでなく、以下を所見として出す
   - 推定読者に伝わらない箇所
   - 原文にない評価、因果、効果、範囲の追加
   - 普段の日本語として浮く語
   - 英日混在で読みづらい語
   - 公式資料やrepo内情報で確認できていない断定
6. 修正版を求められている場合は各問題箇所を書き直す。ただし、入力にない事実、評価、因果、人格を追加しない
7. 修正後のテキストが以下を満たすか確認する：
   - 推定読者が本文だけで要点を理解できる
   - 音読して自然に聞こえる
   - 文の構造が不自然に反復していない
   - 原文の意味と根拠から外れていない
   - 文脈に合ったトーンを保っている
   - バージョン差があり得る内容を、未確認のまま断定していない
8. 不確かな補完が必要になった箇所は、本文に混ぜず短い確認事項にする
9. 依頼種別に合う最終出力を提示する

## 出力形式

依頼に合わせて出力順を変える。

- **レビューのみ**：所見を先に出す。重大度がある場合は重大な順に並べ、必要なら短い確認事項を添える。勝手に全文リライトしない。
- **リライト / 校正 / ブラッシュアップ**：修正版を先に出す。必要な場合だけ短い補足を添える。
- **レビューして修正 / 指摘事項を直す**：主な修正点を短く示し、修正版または変更済みファイルを提示する。

補足に含めてよいもの：

- 推定読者や読者前提（重要または曖昧な場合のみ）
- 根拠不足で具体化しなかった箇所
- 意味が変わるため残した表現
- ユーザー確認が必要な点
- 変更点の概要（有益な場合のみ）

避けるもの：

- 下書き版と最終版の二重提示
- 長い自己批評
- 変更理由の全列挙
- 原文にない事実や意見を足した説明

## 例

**書き換え前（根拠不足）：**

> 山田健診センターは1989年に設立され、地域医療において重要な役割を担い、住民の健康維持に欠かせない存在として、その意義は非常に大きいと言えるでしょう。

**修正版：**

> 山田健診センターは1989年に設立された。

**補足：**

- 「重要な役割」「欠かせない存在」は根拠が本文にないため削った
- 検診件数や地域内での位置づけを入れる場合は、原文または参照資料にある事実だけを使う

**書き換え前（repoドキュメント）：**

> 本プロジェクトにおいては、Project / Goal / PlanVersion / Task / Artifact / AgentRun / Evaluation / ValidationReport / Decision を保存し、PlanVersion を immutable に扱い、再計画は new version と supersede で表現します。Codex などの外部エージェントは MCP 経由で ready task を claim し、成果物と完了結果を登録します。

**修正版：**

> このプロジェクトは、AIエージェントの作業をタスクグラフとして記録する。
>
> 目標、計画、タスク、成果物、判断の履歴を残し、計画を後から上書きせずに変更前後の流れを追えるようにする。
>
> Web UI では計画と進捗を確認できる。タスクの実行や完了記録は、Codex などの外部エージェントが agentflow に登録する。

**書き換え前（未確認の仕様断定）：**

> このCLIオプションを使うと、すべての環境で自動的に設定ファイルが生成されます。

**修正版：**

> このCLIオプションで設定ファイルを生成できるかは、参照資料では確認できていない。

**補足：**

- 対応バージョン、対象環境、自動生成の条件が確認できないため、断定を避けた
- 公式資料またはrepo内で確認できた場合だけ、利用条件を本文に戻す
